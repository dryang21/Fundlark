# v4.3 Manual research-profile workflow

## Step 1 — Tell us about your research

The user enters their research **background**, **proposed project** and **additional keywords**. These are separate, persistent, optional inputs, and explicit keywords take precedence in the first 20 deduplicated matching terms. The browser shows the extracted matching terms so the researcher can adjust them. Quick topic chips populate only the optional keyword input; no CV upload is used.

Career stage is optional. Eligibility fields vary by selected stage. Memberships, institutions, and all applicable eligibility fields are displayed in ordinary page sections rather than collapsible panels. Unknown facts remain unknown; no optional field implies a disqualifying answer.

Prior saved profiles migrate their old free-text `researchText` to the new background field. The optional institution and membership arrays remain unchanged. Because the funding algorithm remains dependent on structured catalog data, more profile information helps precision but is not a guarantee of eligibility.

## Step 2 — My funding dashboard

All plausible personalized leads remain accessible, with funding-source, applicant-route, career-field and eligibility filters and the integrated tracker. *Likely eligible* still means only a provisional assessment based on known catalog facts, not sponsor approval.

## Step 3 — Explore all funding

General search uses a straightforward topic/program/funder input, plus discipline, sponsor, career-stage, support-type, status and sort filters. The existing pagination remains **10 records per page**.

## Tests and limitations

- Unit tests cover topic priority, legacy-profile migration, preservation of independent general exploration, CV-free UI structure, and stage-aware eligibility.
- Browser static-render checks cover 1200px desktop and 375px mobile layouts with no horizontal overflow. Full live interactions were not verified due to browser navigation restrictions in the test environment.
- No new funding records or refreshed deadlines were added.
- The separate historical Python backend (in `app/`) retains its pre-existing CV feature; only the current `docs/demo` static site has removed that feature. Legacy CV review helpers remain for regression tests, but the static website does not load them.
